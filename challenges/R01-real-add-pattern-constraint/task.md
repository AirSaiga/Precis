> 本题在**真实 Precis 仓库**上操作（不是 seed 最小工程）。你需要在数千个文件中
> 定位约束系统的所有相关位置，理解其注册机制，完成一种新约束的全链路实现。
> 与最小 seed 题不同：没有给出任何文件路径，全部需要自己导航发现。

## 任务

在 Precis 后端新增一种 **Pattern** 约束，验证列中的字符串值是否匹配给定的正则表达式。
该约束必须**完全可用**：实现验证逻辑、注册到约束系统、能从配置文件构建、能被校验流水线调用。

### 构造参数

```
PatternConstraint(table, column, pattern)
```

- `table`：表名
- `column`：列名
- `pattern`：正则表达式字符串

### 验证语义

- 列中每个**非空**字符串值，用正则对它做匹配；不匹配的记一条违规。
- **空值（None / NaN）跳过**，不计为违规（与其它约束的空值约定一致）。
- 匹配方式：正则搜索匹配（即 `re.search` 语义，用户可用 `^…$` 自行锚定全匹配）。

## 约束

- 在真实仓库代码里找到约束系统的所有相关文件，完成**实现 + 注册**。
- **不得**修改 `challenges/` 目录、**不得**修改 `tests/` 目录（verify 脚本会自行放置测试文件）。
- 参考已有约束的实现模式——自己找。注意：约束系统不止一个注册表/导出口，遗漏任何一个都会导致测试失败。
- 仓库分层：约束的"类实现"、"类型名→类的注册表"、"类型名→构建参数的注册表"、
  "配置文件的类型字面量"、以及若干"包导出口"分散在不同文件——把链路摸清楚再动手。

## 验证

在本目录运行：

```
python verify.py
```

`verify.py` 会把测试文件复制进后端测试目录并以 pytest 运行；随后还会以相同环境
**回归运行仓库既有的相关测试子集**（`tests/unit/test_validation_constraints_imports.py`）。
注入测试与回归子集**都通过**才算 PASS。
退出码 `0` = PASS，非 `0` = FAIL。stdout 首行为 `PASS` 或 `FAIL`，
随后按 `  [✓]/[✗]` 列出注入测试与回归门明细。

## 提示

- 已有一种"正则约束"存在，但它**没有**进入主注册表——不要照搬它的注册方式，
  要看那些**真正在注册表里**的约束是怎么被全链路接通的。
- 约束实例化走"工厂 + 构建器"两段式：先按类型名查类，再按类型名查构建参数。
- 配置文件的数据模型对 `type` 字段有枚举约束，新类型需要加入该枚举，否则连配置对象都构造不出来。
- 类型名规范化入口维护了一张别名表：多数约束类型都注册了 snake_case / 小写别名
  （如 `'not_null'` → `'NotNull'`、`'allowed_values'` → `'AllowedValues'`），新类型也应照此办理。
- **你的改动不得破坏仓库既有测试**（verify 会回归相关既有测试）。注意：某个兼容层
  re-export 模块的 `__all__` 被既有测试硬编码锁定——接通新约束时若随手把它加进该
  `__all__`，功能虽正常，但会弄坏既有测试导致 FAIL。想清楚"名字绑定"与"列入 `__all__`"
  的区别再动手。
