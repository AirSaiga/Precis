# L05 — 清空画布后的撤销链深层调试（症状驱动 · 双重缺陷）

| 项 | 值 |
|------|-----|
| ID | L05 |
| 类型 | 专家级真实仓库任务（症状驱动调试，故障已注入） |
| 栈 | TypeScript / Vue 3（vitest） |
| 难度 | ★★★+ |
| 预估 | 45-80 分钟 |

> 本题在**真实 Precis 前端仓库**（git worktree / 副本）上操作。评测流程：
> 先在副本上运行 `python plant.py` 注入故障（若已注入会提示），再按下方现象定位修复。
> 题目**不给任何文件路径**——画布状态管理由 20+ 个模块协作，请自行导航。

## 现象（由用户报告，已复现）

画布上先创建若干节点（例如两个绑定同一数据文件的 Schema 节点、一个正则节点，
并建立连接），然后执行**清空画布**：

1. 清空后按 **Ctrl+Z 撤销**——画布恢复了内容，但**恢复的不是清空前的完整画布**：
   最后一步操作（如最近新建的节点）丢失了，像是"回到了更早的中间状态"。
2. 此时再按 **Ctrl+Shift+Z 重做**——画布**又变回空**。
3. 换个角度：清空后不撤销，直接**导入/绑定新的数据源**时，部分重复数据源的
   冲突检测（本应提示"该数据源已被其他 Schema 使用"）似乎失效了。

用户期望：清空画布是可撤销的操作——撤销应恢复**清空前那一刻**的完整画布；
且撤销恢复之后，画布上的一切后续编辑（含数据源绑定与重复检测）都必须正常。

## 任务

1. 复现并**修复撤销/重做链路**：使"清空画布"进入历史，撤销恢复完整画布、重做
   回到清空状态，与其它画布操作（新建/粘贴/删除）的历史行为一致。
2. 修复后**不要止步**：完整走一遍「清空 → 撤销 → 继续编辑」链路，验证撤销恢复出的
   节点在**所有**画布功能中仍然可用（数据源绑定、重复源冲突检测、连接关系……）。
   现象 3 描述的失效可能并不会随着第一步修复自动消失——如果还在，请继续追查并修复。
3. 你的修复**不得破坏**仓库既有测试（verify 会回归画布状态管理相关的一组既有测试）。

## 验收方式（盲验证）

在本目录运行：

```
node verify.mjs
```

`verify.mjs` 会向 `frontend/tests/stores/graphStore/` 注入一份隐藏行为测试（跑完即删）
并以 vitest 执行，覆盖：

- **清空-撤销链（2 分）**：清空操作是否入历史；撤销后画布是否与清空前逐点一致。
- **撤销后一致性（3 分）**：撤销恢复出的 Schema 节点在数据源索引/重复检测中的
  行为是否正确（这是隐藏测试的核心区分项——只修第一步拿不到这 3 分）。
- **回归门（2 分）**：`frontend/tests/stores/graphStore/` 下既有历史/装配/资产/索引/
  剪贴板测试文件全绿。
- **质量门（1 分）**：`src/stores/graphStore/` 目录 ESLint（error 级）0 错误。

评分制输出：stdout 首行 `SCORE: n/m`，随后逐项 `  [i/j] 子项名：说明`。
退出码 0 = 评分完成（仅环境异常才非 0）。隐藏测试文件运行后自动清理。

## 提示

- 画布状态由多个模块协作：历史（撤销/重做快照）、连接状态同步、Schema 数据源索引
  等。某个"清空/重置"路径是否触发了其它路径都会触发的动作，值得逐一对比。
- 关注"撤销/重做恢复画布"之后，那些**依赖画布内容构建的缓存/索引**是否还反映
  恢复后的内容——特别是与数据源绑定、重复源检测相关的那个。
- 修复方式不唯一：可以针对撤销路径补同步，也可以让索引对"内容替换"自适应。
  只要行为正确，隐藏测试都会通过。
- `plant.py --status` 可查看注入状态；`plant.py --restore` 可还原注入（开发用）。
  **绝不要在主仓库运行 plant.py**——只在你自己的评测副本中运行。
