# L03 — 校验引擎吞吐优化（结果必须等价）

| 项 | 值 |
|------|-----|
| ID | L03 |
| 类型 | 真实仓库性能优化 |
| 栈 | Python |
| 难度 | ★★★★ |
| 预估 | 60-120 分钟 |

> 本题在**真实 Precis 仓库**上操作。评分采用多级评分制（满分 9 分）：
> 结果等价（3 分）+ 吞吐档（3 分）+ 回归门（2 分）+ 质量（1 分）。
> **先保证结果等价，再谈吞吐**——等价性挂掉的优化一分不值。

## 背景

数据校验的约束阶段入口是 `backend/app/shared/services/validation/engine.py` 的
`validate_constraints()`：对"已解析数据集 × 全部约束"做校验（约 428 行）。
对于大表（几十万行）配多个约束的常见场景，该校验阶段耗时与内存开销可观。

瓶颈在哪里、怎么优化**由你自己定位和决策**（剪枝 / 向量化 / 预计算 / 快速路径都允许），
但有一个硬性约束：**校验结果必须与优化前完全等价**。

## 任务

优化校验阶段的**吞吐**（单位时间可校验的"行数 × 约束数"），同时满足：

1. **结果等价**：优化后的错误列表与校验详情必须与优化前逐条一致。必须覆盖的边缘包括
   （但不限于）：
   - `None` / `NaN` / 空串等空值的豁免语义；
   - 跨块数据（分块解析后合并）的重复检出、跨表外键；
   - `table_filter` 跳过约束的语义；
   - `stop_on_first_error`（遇错即停）与 `deadline` 超时中断的语义；
   - 空表 / 全空列 / 列缺失等配置错误的输出。
2. **不给方案**：优化方向自选，但修改范围限于后端校验相关实现
   （`backend/app/shared/services/validation/` 与 `backend/app/shared/domain/constraints/`）。
   入口是 `engine.py` 的 `validate_constraints()`——先读懂它如何编排约束执行，
   再用 profiling 找热点（提示：热点可能在它调用的约束实现里，而不是编排循环本身）。
3. 优化必须是**通用的**：不得针对某个具体 fixture 做特判（如硬编码数据形状）。

## 约束

- **不得**修改 `challenges/`、`tests/` 目录。
- 改动必须通过 ruff（后端 pyproject 规则）。
- 不得破坏仓库既有测试（verify 会回归 validat* 簇相关子集）。
- 不要改变约束的**语义**：任何"变快但结果不同"的改动都会被等价测试与回归门拦下。

## 验证

在本目录运行：

```
python verify.py
```

stdout 首行为 `SCORE: n/9`，随后逐行列出各子项得分与说明：

| 子项 | 分值 |
|------|------|
| 结果等价（隐藏 golden 对比，3 个场景各 1 分） | 0-3 |
| 吞吐档（固定 fixture 实测 best-of-3，三档阈值） | 0-3 |
| 回归门（validat* 簇既有测试相关子集全绿） | 0-2 |
| 质量（改动文件 ruff） | 0-1 |

> 注：结果等价子项仅在检测到 backend 代码改动时计分（未改动则等价性无从谈起）。
> 吞吐 fixture 与阈值细节不公开——用真实的热点优化（而不是碰运气）去达标。

退出码 `0` 表示评分完成（仅环境异常为非 0）。verify 会清理注入的测试文件。

## 提示

- 先用既有测试建立基线（validat* 簇与 constraint 簇全部应绿），再动手。
- profiling 建议：用足够大的数据（几十万行）跑 `validate_constraints`，
  按约束逐个计时——找到真正占大头的约束类型。
- 逐行 Python 循环（如逐行字符串检查、逐值函数映射）是最典型的向量化目标；
  注意向量化后的**边界等价**：空值、空串、非字符串值、多字符/生僻字符等。
- 别忘了把 `ruff check` 与回归子集跑绿再验收。
