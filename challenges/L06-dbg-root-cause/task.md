# L06 — 校验"全部通过"却静默丢列（症状驱动的跨模块根因定位）

| 项 | 值 |
|------|-----|
| ID | L06 |
| 类型 | 专家级真实仓库任务（跨模块静默数据损坏链） |
| 栈 | Python / FastAPI / pandas（pytest） |
| 难度 | ★★★+ |
| 预估 | 45-90 分钟 |

> 本题在**真实 Precis 后端仓库**（git worktree / 副本）上操作。评测流程：
> 先在副本上运行 `python plant.py` 注入故障（若已注入会提示），再按下方现象复现定位。
> 题目**不给任何文件路径**——校验系统横跨配置解析、数据引擎、提取、校验、报告聚合
> 多个模块，请自行导航。

## 现象（由用户报告）

一个数据项目在 Schema 里配置了**正则提取列**（`Extracted` 类型：从源列经正则命名捕获组
派生新列，例如从 `email` 提取 `username`），并在数据源里放置了对应的 CSV。

1. 跑**全量校验**，报告显示**全部通过**（格式检查 passed、无任何错误条目）。
2. 但校验返回的解析结果（以及下游预览）里，**提取列整列缺失**——配置里明明写了，
   数据里源列也有值。
3. 服务日志里只有一条 `warning`：「正则提取列 '...' 失败 (来源列: ..., 提取键: ...): ...」，
   报告里却找不到任何对应错误。
4. 换一个项目：给提取列挂上约束后，报错变成一条让人困惑的"约束执行异常"，而不是
   指出提取配置有问题。

用户预期：提取失败必须**显式出现在校验报告**中（作为格式阶段错误），并带足以定位
配置问题的信息；而不是静默通过、列悄悄消失。

## 复现步骤（最小配置）

1. 建一个项目：`project.precis.yaml` + 一个 Schema。Schema 中两列：
   - `email`：类型为 Expr（绑定一个含命名捕获组 `(?P<username>...)` 的正则）；
   - `username`：类型为 `Extracted`（`source_column: email`、`extract_key: username`）。
2. 数据 CSV：**两列表头都叫 `email`**（导出工具产生重复列名，pandas 允许重复列名），
   两列里都有值。
3. 对项目跑全量校验 → 观察：报告全部通过、`username` 列缺失、日志出现上述 warning。

（提示：重复列名只是让"提取过程抛异常"的一种触发方式——任何让提取阶段异常终止的
输入/配置都会走到同一条静默链路。）

## 任务

1. 复现现象，**定位根因**：为什么提取异常没有进入校验报告？（提示：报告的每一类
   错误都有既定的 `stage` / `check_type` 字段惯例——把提取失败的报错路径和"其它
   提取相关错误"（如"源列不存在""未绑定正则""捕获组缺失"）的报错路径对比。）
2. **修复根因**：提取异常必须作为格式阶段错误进入报告，并保留**原始异常信息**
   （这是用户定位配置问题的关键；笼统的"列缺失"提示不算修好根因）。
3. 修复**完整性**：同一 Schema 里多个提取列时，好的提取列必须照常产出、坏的照常
   上报；修复不得中断其余表/约束的校验。
4. 你的修复**不得破坏**仓库既有测试（verify 会回归校验引擎/执行器/服务层的一组
   既有 pytest），并通过 ruff lint（仓库规范）。

## 验收方式（盲验证）

在本目录运行：

```
python verify.py
```

`verify.py` 会向 `backend/tests/unit/` 注入一份隐藏 pytest（跑完即删）并逐项执行：

- **根因（0-4）**：非法正则 → 报告含格式阶段提取错误且**信息包含原始异常内容**（3 分）；
  提取异常上报且不中断其余表校验（1 分）。
- **完整性（0-2）**：好/坏提取列共存时好列照常产出、坏列带原始异常上报（1 分）；
  真实复现路径（重复列名触发）不再静默（1 分）。
- **回归门（0-2）**：校验引擎/执行器/服务行为等 4 个既有测试文件全绿。
- **质量门（0-1）**：`ruff check backend/app`（仓库规范）0 问题。

评分制输出：stdout 首行 `SCORE: n/m`，随后逐项 `  [i/j] 子项名：说明`。
退出码 0 = 评分完成（仅环境异常才非 0）。隐藏测试文件运行后自动清理。

## 提示

- 现象（报告"全部通过"）与根因（某处异常被吞）**不在同一模块**——跟着"提取失败
  warning"这条线索追，看它产生的地方为什么不把错误放进报告。
- 先读该模块的 docstring：它自己承诺了"提取失败作为验证错误返回，避免静默通过"。
- 对比同一文件里其它提取失败分支的报错字典结构（`stage`/`check_type`/`column`/
  `message`），修复时保持字段惯例一致。
- `plant.py --status` 查看注入状态；`plant.py --restore` 还原（开发用）。
  **绝不要在主仓库运行 plant.py**——只在你自己的评测副本中运行。
